## Conventions

- Ids are UUIDv7-shaped (`public_id`, item, variant, option and modifier ids (API-18), option group ids (API-20), hold, staff, branch). The View Model fixtures use slugs; the API uses public ids, so the same item, option or group has a different id here. Human labels stay where the schema has them (`label`, `choices_label`). The "If it's out of stock" group is store-defined (API-22): its options are option ids, the same group in `GET /store` and on the item, and `CartLine.substitution` / `substitution_preference` send one of them.
- Times are ISO 8601 with the store offset (`+03:00`, Asia/Riyadh); `Date` response headers are the same instants in GMT. Today in the examples is Fri 2 Oct 2026.
- Every write carries an `Idempotency-Key` (UUIDv7) and an `Origin`. The legacy order body sends `client_uuid` instead: the header is required with the new body only, and stays optional on the legacy body until the sunset (API-17, README §2.7).
- Booking days, slots and holds pass the chosen `option_ids` with the `service_ids` (options change the duration). A quote whose `requires` lists `return_url` sends `payment_mode: hosted`.
- Tokens (`sfx_demo_…`, `trk_…`, `mgt_…`, `hld_…`, `ctk_demo_…`) are fake. A kiosk token has `_kiosk_` in its value (`sfx_demo_sidra_kiosk_0001`); the checker uses that to apply the kiosk rules (API-15).
- Owner decisions API-8…34 (`../README.md` §8) are applied: `payment.next_action.expires_at` is the response `Date` + 15 minutes (API-10); `reschedule_deadline_at` always equals `cancel_deadline_at` (API-9); reschedule slots and holds use `X-Manage-Token` and the reschedule leaves `payment` unchanged (API-8); a late payment leaves the order `cancelled` with `received_late` (API-21); a bound hold is released only with the store setting on (API-24a), booking-deposit holds included (API-26); every substitution option has exactly one picker action (API-25); an accepted late payment is `placed` / `confirmed` when the slot was re-reserved, else `pending_approval` with the money `paid` or `authorised` (API-27); a `call_customer` option names its no-answer `fallback` (API-30); a late card hold that lapses in `pending_approval` leaves the order `cancelled` with the hold `voided` (API-32).
- Legacy bodies use integer ids and float prices, as Juwri answers today (`LegacyMenuResponse`, `LegacyRestaurantResponse`, `LegacyTrackResponse`, `LegacyOrderCreated`); values are illustrative.

## Check

```
python3 kit/api/check_examples.py              # all examples + self-test; exit 1 on any failure
python3 kit/api/check_examples.py --self-test  # only prove a broken example fails
python3 kit/api/check_examples.py --lenient-oneof kit/api/examples/food/*.json  # overlapping oneOf = warning
```

It resolves each operation by `operationId`, checks method, path template, required headers and parameters, and validates request and response bodies against `openapi.json` (following `$ref` into `../viewmodel/viewmodel.schema.json`). It also checks the quote totals against the design totals, the totals-parity rules of `tools/conformance/totals_parity.py`, and cross-file rules per flow (echoed `quote_hash`, hold id and token, tokens from the create response, idempotent replays). Overlapping `oneOf` branches are errors by default. It also enforces the spec rules OpenAPI cannot express: `Idempotency-Key` per order body type, `requires: return_url` exactly with `payment_mode: hosted`, the `weighed` estimate/cap formula, `refunded_amount` on refunded payments, the deposit outcome on a cancelled booking, and decisions API-8…34: UUIDv7 option and option group ids, `reschedule_deadline_at` = `cancel_deadline_at`, the 15-minute payment window, same-price reschedule with a booking-tied hold and no money moving, the verified customer token from the OTP flow, the kiosk exemption, `kiosk_not_enabled` details, `received_late` only on a cancelled order without `next_action`, substitution options from the item's and the store's groups, and `releaseHold` 200 only with "Release holds during payment" on (409 `hold_in_use` only with it off), for order and booking holds, cancelling the record the hold was bound to (API-26); exactly one valid picker action (`offer_replacement`, `call_customer`, `remove_item`) per substitution option, in the store's group and on the item (API-25); after a late payment the same record goes ahead paid or authorised, or waits as `pending_approval` with the money accepted, and a booking is `pending_approval` only after a late deposit (API-27); a `fallback` (`offer_replacement` or `remove_item`) on every `call_customer` option and on no other (API-30); `authorisation_expires_at` only on an `authorised` or `voided` payment, and an accepted card hold still `pending_approval` after it lapsed must be `cancelled` with the hold `voided` (API-32). The full run also fails if the pack lacks a booking release with the setting on and off, an order release, either API-27 outcome, or a late card hold that lapsed in `pending_approval` (API-32).
