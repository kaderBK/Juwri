How a request is protected

The changes close gaps at the earliest practical layer, then preserve endpoint-specific authorization and business validation behind that boundary.

01 ingress Host and proxy trust

Reject poisoned hosts. Trust forwarded values only from configured proxy addresses or CIDR ranges.

02 transport Origin and CSRF

Browser MCP origins are exact matched. Session writes keep CSRF. Only explicit provider callbacks bypass it.

03 identity Header-first auth

Bearer and storefront headers are the production default. Query credentials require an explicit compatibility switch.

04 authorization Role and tenant scope

Admin, owner, staff, reseller, customer, password confirmation, and store boundaries decide access.

05 execution Validation and audit

Rate limits, provider signatures, validation, idempotency, logs, queues, and release gates protect side effects.

MCP-C

MCP Streamable HTTP modernization

All five MCP servers now default to the 2025-06-18 protocol, retain negotiated legacy support, validate browser origins, return 202 for accepted notifications, and reject GET transport use.

Verified

Behavior now

  • Endpoints: /mcp, /mcp/dev, /mcp/storefront, /mcp/catalog, and /mcp/customer.
  • Supported versions: 2024-11-05, 2025-03-26, and 2025-06-18.
  • The initialize default is 2025-06-18. A supported requested version is echoed.
  • No Origin is accepted for normal CLI/editor clients. A present Origin must be same-origin or exactly listed in MCP_ALLOWED_ORIGINS.
  • Notification-only POST requests return HTTP 202 with no JSON body. Mixed batches omit notification responses.
  • GET returns 405 with Allow: POST. This implementation does not expose an SSE stream.

OPS-E

Failure-safe deployment workflow

Deploys cannot silently skip health verification, cannot proceed without required configuration, and use an EXIT trap to restore service after any failure inside the maintenance window.

Implemented

Deployment lifecycle

  • A preflight job verifies all six required secrets before SSH.
  • The remote script uses set -eu and registers restore_service on EXIT.
  • artisan down --secret uses a required maintenance bypass secret.
  • git pull --ff-only refuses implicit merges.
  • Dependencies, migrations, assets, config, routes, and views are rebuilt under the maintenance window.
  • artisan up runs on success, and the EXIT trap retries it when a command fails.
  • A mandatory configured health URL must return success.
  • No automatic source reset claims to reverse a forward database migration.

Required GitHub secrets

  • DEPLOY_HOST
  • DEPLOY_USER
  • DEPLOY_SSH_KEY
  • DEPLOY_PATH
  • DEPLOY_UP_SECRET
  • DEPLOY_HEALTHZ_URL

How to operate and test

  • Configure the health URL with the production HEALTHZ_TOKEN query value when detailed readiness is protected.
  • Review every migration for expand, backfill, and later contract compatibility before release.
  • Prefer atomic release directories with a symlink switch where the host supports them.
  • In staging, force a failure after artisan down and prove the application returns from maintenance while the workflow still fails visibly.
  • Confirm supervisor rotates worker.log at 50 MB with 10 backups and restarts workers on new code.
A successful workflow definition is not deployment proof. Failure injection, queue restart, health monitoring, backup restore, and migration-compatible recovery remain operator-run scenarios.
SEC-F

API transport, health, proxy, and host boundaries

Production credentials default to headers, health details default to private, forwarded headers require explicit proxies, and trusted hosts include verified tenant domains without accepting arbitrary Host input.

Verified

What changed

  • TOKEN_QUERY_FALLBACK defaults to false in production. Local and test environments retain explicit compatibility unless disabled.
  • Owner and storefront token middleware accept query credentials only when the setting is enabled. Deprecated use is surfaced.
